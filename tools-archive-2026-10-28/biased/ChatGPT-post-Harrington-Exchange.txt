# Harrington Exchange — Any-Width Swap/Juggle Tests (28 October 2026)
**For review. Raw data, method, my insights and open questions. Please be critical.**

## 1. What the Harrington Exchange is

It is a reversible two-step transform applied before a standard compressor (zstd here).

1. **Swap (rename by frequency).** The data is cut into fixed-width chunks of *J* bits (the "juggle" width). The chunk values are ranked by how often they occur, and the most frequent values are renamed to the most "desirable" bit patterns. Here "desirable" means the most zeros in the leading *S* bits, then the most zeros overall. Only the top K = 256 values are mapped explicitly. The map is completed to a full permutation: values displaced by the mapping are sent back to the source values that were freed, in sorted order. This makes the transform exactly invertible.
2. **Juggle (split).** Each renamed chunk is split at bit *S* (the "swap" size). The first *S* bits of every chunk go to stream 1, and the remaining *J − S* bits go to stream 2, which is stored in reverse order.

Each stream is compressed separately with zstd. The rule is S < J. The method was originally designed for **random data with a bias**, not for structured files.

**How I implemented the user's instruction ("swap smaller than juggle").** S is the split point, i.e. the leading bits that form stream 1. J is the full chunk width that is renamed and split. The user may define "swap size" differently; please flag it if this reading looks wrong.

**Two stream layouts were tried, and the smaller kept:**
- *tight* — bits packed back to back;
- *byte-aligned* — each chunk's part right-aligned in whole bytes.

**Header cost charged:** 2·K·J bits for the map + 4 bytes + any leftover tail bits (stored raw).

**Measurement:** compressed size only, exact round trip not separately verified in this sweep (the permutation is invertible by construction). **Decode speed was not timed.**

## 2. Test protocol (as instructed by the user)
- Enumerate **swap S = 1 … 23**, and for each S, **juggle J = S+1 … 24**. That is 276 combinations per file, including all odd widths and 1-bit swaps.
- To save time, every combination was scored with **zstd -3**, and the **top 3 were re-scored with zstd -19**.
- Baselines: plain zstd -3, zstd -19, xz -9e (biased-data run only).
- Fairness checks against **known** transforms: byte shuffle (split multi-byte samples into byte planes), bitshuffle (bit planes), and unpacking odd-width symbols into whole bytes.

## 7. My insights
1. **The Exchange is not for structured files.** On text and database data, zstd's own match finding already captures the structure, and the split scrambles it (+0.4% to +27%).
2. **The width must match the data's natural symbol size.** Every win was at J equal to the true symbol width or a simple multiple of it:
   - 16 for the 16-bit images;
   - 12 for the 12-bit noise;
   - 5 or 10 for the 5-bit symbols;
   - 24 for the 24-bit EEG;
   - 21–22 for the packed biased bits, where no natural width exists and the optimum is broad (S/J = 9/13 through 16/24 all within 2%).

   Odd widths only matter when the data really is packed at odd widths.
3. **On packed odd-width data the Exchange beats zstd, xz, bitshuffle and unpack-to-bytes.** The clearest case is the 12-bit noise, where it lands within about 1% of the theoretical order-0 bound. Splitting each 12-bit sample at bit 4 separates the noisy low bits from the predictable high bits.
4. **The renaming step's contribution is unproven.** On the 5-bit file, simply unpacking to bytes ties the Exchange, which suggests most of the gain there comes from re-aligning the symbols, not from the frequency renaming. An ablation (split only, no swap) is needed.
5. **Real-data evidence is thin.** The two clean wins are a synthetic file and NIST's biased-bit test file; the real 24-bit EEG lost to plain byte shuffle.
6. **Decode speed is unknown.** The Python prototype is not a fair speed test; a C implementation is needed.

## 8. Caveats
- Compressed size only; decode speed not measured.
- The synthetic files were made by me to match the method's design, so they favour it by construction.
- The zstd -3 → zstd -19 two-stage scoring could miss combinations that only win at -19.
- K = 256 was fixed for the full sweep; larger K might help at large J.
- My reading of "swap" (split point) versus "juggle" (chunk width) may differ from the author's.
- Single runs; sizes are deterministic, but no timings were taken.

## 9. Questions for the reviewer
1. Is there prior art combining frequency-ranked renaming with a bit-position split at arbitrary widths? Known neighbours are bitshuffle, byte shuffle, and symbol remapping in entropy coders.
2. What real datasets are naturally packed at odd bit widths? Candidates: 10/12/14-bit camera RAW, packed sensor telemetry, CCSDS space packets.
3. Is the near-entropy result on the 12-bit file expected for any correctly aligned split followed by zstd's entropy stage, or is the renaming doing real work?
4. What is the best way to choose S and J automatically without a 276-combination search?
