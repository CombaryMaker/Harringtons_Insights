HARRINGTON SETS ON NON-COMPRESSION SOFTWARE: jq AND river
30 October 2026. 2-core cloud machine, wall clock, single-core tools left unmodified.
Software here: hs_lines.py (line-record variant of the Harrington Sets wrapper), make_data.py (test data),
filter.jq, river_score.py, auc.py, river_rust_stub.py. Michael Hugh Harrington, MIT License.

WHAT CHANGED IN THE WRAPPER
Windows are about 64 KB but end at a line end, and a marker line goes in front of each window so that every
window's output can be put back in its original place. Everything else is the same method (7 features, raw
exclusion, k-means up to 3 sets, folding, smoothing, equal blocks, parallel copies).

TEST DATA (synthetic, made by make_data.py)
JSON Lines, three sources (environment sensor, network counters, app log with text) in long sections of
0.5-4 MB, 1% planted anomalies. jq file: 52,428,830 bytes, 726,497 records. river file: 62,914,565 bytes,
918,169 records.

NOTES
- jq: works; correct output every time; speed-up is modest because jq is fast and the wrapper's reading and
  reassembly in Python is a large part of the time. Grouping adds little speed for a tool that does not learn.
- river: no real speed-up on 2 cores (each copy restarts Python and river, about 1 s, and 9 blocks on 2 cores
  run in 5 rounds). The gain is in detection: split streams found about twice the anomalies of one stream,
  and Sets beat equal blocks slightly on the large run. Much of that gain comes from splitting itself (each
  copy rescales to cleaner data), not only from grouping.
- The byte features separated the text source (app) from the numeric ones, but put the two numeric sources
  (environment and network) in one set; their bytes look alike. A field-aware feature would split them.
- river was run from its GitHub source because the package installer was blocked; its Rust extension could not
  be built, so river_rust_stub.py stands in for it (HalfSpaceTrees and MinMaxScaler are pure Python and do not
  use it).
- Synthetic data built to be mixed; results on real logs may differ. Single runs on river.
- The three sources share the same three numeric fields (f1-f3), which mean different things per source.
  That is what makes one model fail; a pipeline that keys fields by source would do far better with one
  model. Sets had the best hit rate on both river runs; equal blocks had the better AUC on the small run.

WHY THE ANOMALIES MATTER
The anomalies are the 1% of records made abnormal on purpose (sensor 40 degrees instead of about 23, network
latency 40 instead of about 12, app response 400 ms instead of about 120), standing in for failing sensors,
network attacks or slowdowns. They measure whether the tool finds the problems, not only how fast it runs.
One model watching the mixed stream had its sense of scale stretched by network values near 180,000, so a
temperature spike looked like nothing, and it did barely better than chance. Split streams gave each copy a
narrower mix, so the same spike stood out and the catch rate doubled; Harrington Sets did best by also
separating the text-heavy app records. Use: one detector on a mixed feed with no per-source setup (security
monitoring, sensor networks, fraud screening). Limit: 24% caught is still low, and a detector set up by hand
for each known source would do far better; the advantage is needing no such setup.
