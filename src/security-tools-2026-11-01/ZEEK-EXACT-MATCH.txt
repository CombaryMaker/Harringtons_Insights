RESULT
  One 903 MB public capture (964,792 packets), split into 2, 4 and 8 shards, run by separate Zeek processes, merged:
  every log row identical to the plain single-process run - 35,920 of 35,920 rows in all 17 compared logs (conn, dns,
  http, files, ftp, smtp, snmp, ssl, x509, dhcp, weird, notice, signatures, known_hosts, known_certs,
  known_services, software), for 2, 4 and 8 shards. Not compared: logs about the Zeek process itself (stats,
  loaded_scripts, packet_filter, capture_loss, reporter, telemetry).
  Condition: max_timer_expires = 0 in both the plain run and the shard runs (notimerthrottle.zeek). See "TIMER CAP".
  Plain Zeek is itself repeatable: two plain runs, 35,920 of 35,920 rows identical.

WHAT WAS NEEDED (beyond the first version in RESULTS.txt)
  1. Clock ticks (hs_pcapsplit --ticks). A shard only sees its own packets, so its Zeek clock jumps where the plain
     run's clock moves in small steps, and timers (connection timeouts, table expiry, delayed events) fire at other
     network times. Each shard now also gets a 60-byte frame with EtherType 0x88B5 (IEEE local experimental) at
     every time a packet went to another shard. Zeek reads these frames without logging anything; the shard's clock
     now moves exactly as in the plain run.
  2. Raw inputs + replay (hs_shard.zeek, hs_zeek_merge.py). software.log and known_services.log are decided from
     per-host / per-server tables (Zeek 8 base/frameworks/software/main.zeek, policy/protocols/conn/
     known-services.zeek). One server answers many clients, and the clients are in different shards, so no single
     shard has the whole table. Each shard records every input to those decisions (Software::register and
     Known::service_info_commit, before Zeek checks its table) with its network time. The merge replays Zeek's own
     rules over all shards' inputs in Zeek's processing order:
       - network time first; at one network time, timers fire before the packet's own events, in order of their
         scheduled time (a known_services commit for a connection without a service is scheduled 5 min later);
       - software: per host a table that expires 1 day after the host entry is created; logged when the name is new
         for the host, the parsed version differs, or force_log is set;
       - known_services: per (host, port, protocol) a set of services expiring 1 day after creation; an input is
         logged with the services not yet in the set, unless the entry exists and already has them all.
     Self-test: replaying the plain run's own recorded inputs reproduces its software.log and known_services.log
     exactly (35,920 of 35,920 rows).
  3. Bugs found on the way: port 53/tcp and 53/udp were first treated as one key; delayed commits firing at the same
     network time were first ordered by shard instead of by scheduled time.

TIMER CAP (max_timer_expires)
  Zeek's default max_timer_expires = 300 lets at most 300 due timers fire per packet; the rest wait for later
  packets. How long a timer waits therefore depends on how many other timers are due at that moment, i.e. on the
  whole traffic load. A shard carries less load, so its timers fire on time. With the default, the only difference
  left is one known_services row per capture copy (6 rows of 35,920): a DNS server's entry stamped 1200001215.968523
  in the plain run and 1200001213.976013 in the shards. With max_timer_expires = 0 ("process all expired timers with
  each new packet", Zeek's own documented value) the plain run also stamps it 1200001213.976013.
  Setting it to 0 did not slow the plain run here: 10.39 s and 11.74 s (two runs) vs 10.44 s and 10.76 s with the
  default.

  (zeek s and split s from bench_zeek3_t0.log; merge s is the final merge version, timed separately.)
  Cost of exactness: every shard reads a clock tick for each packet that went elsewhere (964,320 ticks per shard
  at 2 shards). A tick costs about a third of a real packet here, so on 2 cores only 2 shards pay off. With 4 or 8
  shards on 2 cores the shards wait for each other; the many-core result is not measured yet.
