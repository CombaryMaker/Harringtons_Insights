WIKIPEDIA SEGMENT-TYPE TEST (10 Nov 2026) - Michael Hugh Harrington's idea. Cloud machine.
Data (public): three 4 MiB slices of enwik8 (the Hutter Prize test file's first 100 MB), from 0, 40 and 80 MiB.
Line kinds: prose, heading, list, template/table/fact box, indented (code, XML page data), category/language link,
escaped tag (&lt;...), any line in a References / External links / See also / Notes section, blank.
Share of the slices: prose 63-69%, lists 12-14%, reference sections 9-10%, indented/XML 5-8%, templates 3-4%.

A. SEGMENT-TYPE CONTEXT INSIDE LPAQ1 (lpaq1w.cpp; nothing stored - the kind is read from each line's first bytes as
   they are coded, plus the previous line's kind and whether we are in a reference section). Every slice decoded
   exactly. Fair control: the same model with a plain sparse context in that slot (both have the word-pair context).
   slice   stock lpaq1   control    segment context   vs control   vs stock

   s40       931,431     925,201      920,694          -0.49%       -1.15%

FINDINGS
  - The segment-type context is the winner: about half a percent better than an equal plain context on every slice,
    with nothing stored - larger than any gain on the novels. Wikipedia's marked switches make the kind cheap to know.
  - Grouping lines by kind helps HCM and xz a little after paying for the note, is about even for kanzi, and hurts
    lpaq1 and BSC. With the segment context inside the model, grouping only hurts: the context already captures it.
  - Next: richer segment contexts (kind with the word, with place in the line, template field names, reference-section
    layout) and a cheaper note.
